# gz-ops — local ops API contract

The contract that the server control panel, launcher, GM tool and the eventual
ops server all agree on. **Contract only**: framing, message types, generated
schema. No server, client or transport implementation.

T-010 (M0). See `docs/rust-rewrite/tasks/T-010-ops-api-draft.md` and
plan §9.

---

## 1. Scope

Consumed by three local-only Tauri apps (plan §9): **control panel**,
**launcher/patcher**, **GM tool**. All three are sidecars on the operator's
own machine, and all three wrap `gz-ops` through `goonzu-tauri-core` (Rust) —
so the transport is always Rust-to-Rust and never something JavaScript has to
speak.

Deliberately **not** in this crate: a listener, a client, a database driver, or
any game-protocol code. It must stay consumable from a plain frontend core
crate.

### Artifacts

| File | What it is |
| --- | --- |
| `schema.json` | the contract as JSON Schema 2020-12, 39 `$defs`. **Derived**, never hand-edited. |
| `schema-examples.json` | 13 requests + 15 responses + 1 event, as the real serializers emit them |
| `../tests/contract.rs` | 16 tests that keep the above honest |

Both JSON files are regenerated by:

```
cargo run -p gz-ops --bin export-schema
```

and checked for drift (without writing anything) by
`cargo run -p gz-ops --bin export-schema -- --check`, which `check.ps1` step 5
runs. `tools/schema-check/validate.js` additionally validates the schema
against a real validator and asserts that malformed frames are **rejected**.

## 2. Transport

### Recommendation: Unix domain socket at mode `0600`, with a token as backup

T-010's card suggests "localhost TCP, length-prefixed JSON lines; token from a
local file". The framing half of that is adopted (see §3). The transport half
is **not**, and this is the one place the card is deliberately departed from.

The argument:

- **A local ops channel that can start services, edit config and later kick and
  ban players is effectively root-equivalent on the game server.** It deserves
  an access control that actually enforces something.
- **A `0600` Unix socket does.** Only processes running as the operator's UID
  can connect. That is enforced by the kernel, not by a secret on disk.
- **TCP plus a token file mostly does not.** Every process running as the same
  user can read the token file, so for the realistic threat — another process
  on the operator's own account — the token adds nothing. And any listening
  TCP port is a permanent local attack surface with no upside, because the
  consumer is on the same machine.
- **The JS side never touches the transport.** Tauri proxies it through Rust
  commands regardless, so "JavaScript can't do Unix sockets" is not a cost.

So the recommendation is Unix socket at `0600` on Linux (the deployment
target), with the token still carried for defence in depth — it matters when
the socket is behind a proxy or bind-mounted, and it costs one field.

### Windows fallback: loopback TCP + token

Not a preference — a constraint. `tokio` has no Windows named-pipe server, so
on the dev machine there is no socket type that is both local-only and
ACL-checked. Loopback TCP + token it is. The framing and message types are
identical, so this is purely a listener choice, and it lives in the
implementation, not here.

| | Linux (deployment) | Windows (dev) |
| --- | --- | --- |
| transport | Unix stream socket, `0600` | `127.0.0.1` TCP |
| primary control | filesystem permissions | token |
| token | recommended | required |
| bind failure behaviour | fail loudly | fail loudly |

**Binding must never be "fall back to something weaker silently."** If the
socket path is taken or perms cannot be set, the server exits. An ops channel
that quietly listens on an open port is worse than one that is not running.

### Service name registry

`services.list` reports the Rust workspace's service names. The legacy
`.vcproj` names differ, so a mapping has to exist somewhere; this is the
probable one, to be confirmed against the supervisor in M5 rather than
asserted here:

| registry name | legacy project | note |
| --- | --- | --- |
| `front` | `Server\FrontServer\FrontServer` | |
| `auth` | `Server\AuthServer\AuthServer` | regional variants exist (`AUTHSERVERCHINA`, `JapanAuth`) |
| `game` | `GoonZuWorld\GoonZuWorld` | |
| `logd` | `GoonzuUserlog\GoonzuUserlog` | the untranslated fork — see §8 |
| `supervisor` | `AdminSystem\MasterServer` + `AdminSystem\ServerAgent` | per the supervisor's own README |

## 3. Framing

```
frame := u32_be length | payload[length]
payload := UTF-8 JSON object
```

`MAX_FRAME_BYTES` is 65536. The 4-byte prefix is consumed by
`gz_ops::framing`; implementors do not re-implement it.

### Why not newline-delimited JSON

Because **everything on this channel is untrusted text**: log lines, player
names, config values, driver error messages. Any of them can contain `\n`. A
CP949→UTF-8 conversion can produce one. A crafted character name can. The
moment the receiver splits on newline instead of length, one such payload
desynchronises the stream — the tail of the string parses as a fresh frame and
every subsequent request is off by one.

The same reasoning makes the length prefix, rather than a `\0` sentinel or a
length-plus-`\n` hybrid: it has exactly one way to be wrong, and that way is a
compile error in `framing::decode`.

This is not hypothetical caution. The same class of bug cost a day on the LZF
oracle during T-005, where a hand-transcribed test vector was silently the
wrong length.

### Oversized frames are fatal

A frame declaring more than `MAX_FRAME_BYTES` closes the connection. It is
tempting instead to read-and-discard the declared length so the stream
resynchronises; that is a denial of service, since a peer can declare 4 GiB and
then dribble bytes. For a local tool talking to a supervisor it can restart,
one reconnect is cheap.

A **zero-length** frame is also an error. "Empty payload" should have exactly
one meaning.

## 4. Envelope

```jsonc
// request
{ "id": 1, "method": "status.get", "params": {} }

// success
{ "id": 1, "ok": true,  "result": { "method": "status.get", "data": { … } } }

// failure
{ "id": 1, "ok": false, "error": { "code": "not_implemented", "message": "…" } }

// push (only after logs.tail)
{ "subscription": 1, "event": "logs_line", "data": { … } }
```

**A frame is a response if and only if it has an `ok` member.** Anything else
is an event. The two cannot collide: a response always carries `ok`, an event
never does. That is the entire routing rule.

`ok == true` ⇔ `result` present. Enforced by `Response::ok` /
`Response::error`, and asserted in `tests/contract.rs` for every variant.

### Not JSON-RPC 2.0

The shape is familiar; the `jsonrpc: "2.0"` member is deliberately absent. Both
ends are Rust processes holding generated types, so there is no third-party
client who would recognise the standard, and dropping it keeps frames smaller
on the log-tail path, which is the highest frame rate on this socket.

### The `method` discriminator inside `result` / `data`

`result` is `{"method": …, "data": …}` rather than the bare payload, and the
`data` shape is method-specific. That is the price of a schema a frontend can
generate types from: `status.get`'s result and `services.list`'s result are
different shapes, and a frontend needs the schema to say so.

### Notes on the individual shapes

**`ops.hello` is mandatory and must be first.** It is what lets the control
panel say "this server is too old" instead of firing a request the server
rejects with a bare `method_not_found`.

**`config.get` never returns a secret's value.** `ConfigEntry::secret` comes
back with `value: null`, always. Plan §9 requires DB credentials to live in
the OS keychain; config is readable by anything that can reach the socket, and
root can read the keychain anyway, so hiding the value only here would move
the leak from a documented place into an undocumented one. The frontend gets a
key name and a "set a new value" affordance.

**`logs.tail` sets two flags that exist because of how the alternatives fail.**
`LogLine::truncated` — a line over the per-line budget was cut. A client that
ignores it silently renders a sentence that does not end where the log does.
`LogLine::lossy` — some bytes were not valid CP949 and were replaced. A log
full of mojibake is a *configuration* problem (wrong source encoding) and the
operator has to be told, not left to guess. Also: `seq` gaps mean lines were
dropped because the client fell behind, and the UI must say so.

**`config.set` never restarts anything.** It reports `needs_restart` and stops
there. Restarting is a separate, deliberate action, so an unrelated edit can
never take a service down.

**`players.list` is typed but not backable.** `gz-db` models only
`Account` (M1); the character repository is M2/M3. See §8.

## 6. Versioning and compatibility

`API_VERSION` is 1. Bumped when a method is added or a payload grows an
**optional** member.

A newer server must keep older clients working, so additions are the only
sanctioned change. A removed method, a removed member, or a changed type is a
major bump, and affected clients fail `ops.hello`'s `min_api_version` check
with `invalid_params` instead of discovering it at runtime.

## 7. Config

`config.get` / `config.set` are typed against a **TOML** config
(plan §9's "validated TOML" config editor), serialised to JSON on the wire.

There is currently **no server config file in the workspace** — no TOML
outside crate manifests. So both methods return `not_implemented`, as does
everything else outside the read-only phase. Typing them now is the point of a
contract draft: the frontend can be built against the finished surface instead
of a subset that changes underneath it later.

## 8. Open questions — owner decisions needed

These are recorded rather than guessed at.

1. **`players.list` shape.** `PlayerSummary` carries `player_id`, `name`,
   `online` and nothing else. The legacy character schema has not been
   surveyed; adding fields is a breaking change to the type, so they should be
   added once, when the real columns are known, rather than guessed now and
   corrected later. Needs the M2 character work to settle.

2. **`GoonzuUserlog\GoonzuUserlog\ITZNetLib\`** — an untranslated fork holding
   a second, divergent copy of `ITZMap.cpp`/`.h` and `ITZCell.h` (223 vs 312
   lines, different MD5). It sits directly on the `logd` path this contract
   reports on. Which copy is authoritative?

3. **Log source encoding.** `LogLine::lossy` assumes CP949/EUC-KR, per the
   translation work. If any log stream is UTF-8 already, `lossy` will not be
   able to tell "correctly decoded" from "decoded by luck".

4. **`config.set` in the read-only phase.** The card lists it there; it
   writes. Implemented here as typed-and-stubbed. Confirm that is what was
   meant rather than dropping it from the read-only phase.

## 9. Guarding the contract

Drift is made loud rather than silent:

- `Method`, `Call` and `ResponseData` must agree on names and arity —
  asserted in `tests/contract.rs`.
- `schema.json` and `schema-examples.json` are derived from the Rust types by
  `cargo run -p gz-ops --bin export-schema`, and a test fails if the committed
  files differ. Same arrangement as `codegen --check`.
- The method table in §5 is generated from the same metadata, so it cannot
  describe a method that does not exist. The exporter panics if the README
  loses its delimiters, rather than quietly doing nothing.
- No part of the schema may accept `null`. Every `Option<_>` carries
  `skip_serializing_if`, so serde omits an absent optional rather than sending
  null; a schemars transform strips the `null` it would otherwise emit, and a
  test walks the whole schema to prove none survives.
- The `ok`/`result`/`error` invariant is in the schema as `if`/`then`, not just
  in prose.

### Two defects this found

Both were invisible to the Rust tests at the time and would have shipped a
contract that lied to its consumers.

**`{"ok":true,"result":null}` validated.** schemars does not account for
`skip_serializing_if` when deriving types, so it emitted `null` as acceptable.
A frontend generated from that schema carries a `result` it must null-check, and
its failure mode is a null deref rather than a rejected frame.

**`{"ok":true}` with no result at all validated.** JSON Schema's `required` is
unconditional, so "`ok` is true ⇒ `result` is present" is only expressible as
`if`/`then`.

### Verifying against a real validator

`cargo test` proves the schema matches the Rust types. It cannot prove the
schema describes the wire format, because the two are the same source. For
that:

```
cd tools/schema-check && npm install && node validate.js
```

21 checks, including 15 malformed frames that must be **rejected**. A schema
that accepts everything passes every positive check while being useless to a
frontend, so the negative cases carry half the weight. See that tool's README
for the full list and for the falsification table.

### Note on `uint32` / `uint64`

Integer members carry `format: "uint32"` / `"uint64"` to record the Rust source
width. These are **not registered JSON Schema formats** — they are annotations,
and a strict validator warns about each one. Register them as no-ops before
compiling; `schema.json`'s own `description` says so. They are kept
deliberately: a `u64` above 2^53 does not survive a round trip through a
JavaScript `Number`, and the frontend needs to know which fields those are.
