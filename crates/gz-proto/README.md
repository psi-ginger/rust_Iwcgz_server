# gz-proto

Wire types, generated opcode enums, and packet codecs (blueprint 01).

## Generated modules

| Module | Source | Entries | Ids |
|---|---|---|---|
| `opcodes_game` | `GoonZuWorld\CommonLogic\MsgType.h` (`eGameNetworkMsg`) | 1621 | 1–8438 |
| `opcodes_front` | `Server\FrontServer\FrontMsg.h` | 41 | 1–30000 |
| `opcodes_auth` | `Server\AuthServer\AuthMsg.h` | 34 | 1–10000 |

All three are generated by [`tools/codegen`](../tools/codegen) — **do not edit by
hand**. Regenerate with `cargo run -p codegen -- all`.

```rust
use gz_proto::opcodes_game::{self, GameMsg};

assert_eq!(GameMsg::RequestChat.id(), 117);
assert_eq!(opcodes_game::name(117), "GAMEMSG_REQUEST_CHAT");
assert_eq!(opcodes_game::from_id(12), None); // 12 is inside a reserved gap
```

### Why these numbers are load-bearing

The shipped client is unchanged, so every opcode must match the legacy server
byte for byte. The generator is cross-checked in `tests/` against values taken
independently from the blueprint: the 53 explicit rebase anchors and 157 inline
`//NNN` annotations for the game table, and the full §4.2 / §5.1 row lists for
front and auth.

Three properties worth remembering when reading the tables:

- **The numbering is sparse on purpose.** The legacy developers rebased to round
  numbers and left gaps (12–76, 151–199, 25–999 on front, …) reserved. Never
  renumber to "tidy it up" — some legacy producers may still emit them.
- **Nothing reaches `0x8000`.** Bit 15 of `usCmd` is the LZF compression flag, so
  an opcode at or above `0x8000` would be indistinguishable from a compressed
  packet. A test enforces this on every table.
- **Dead opcodes are still generated.** Blueprint §5 gaps recommend dropping
  front opcodes 5, 6, 9, 9000, 9001, 1004, 1005 in the rewrite. That is a
  *server* policy decision for a later milestone; the table keeps them because the
  client's numbering must stay intact.

### Link-specific notes

- **Game:** 1621 live entries. `GameMsg::End` (8438) is the legacy `GAMEMSG_END`
  terminator, not a real message; the highest real message is 8437.
- **Front:** the highest opcode is `FRONTMSG_RESPONSE_SECRETKEY = 30000`, which
  carries the ITZ cipher keys. Blueprint §1.5: the server must send it before any
  encrypted message or the client will never leave the login screen.
- **Auth:** 34 entries from the full `Server\AuthServer\AuthMsg.h`. The
  China-only `Server\AUTHSERVERCHINA\AuthMsg.h` (12 entries) is out of scope per
  blueprint §5.1 and is not generated.

### Known deviation from the blueprint

Blueprint Part B §1.1 reports "1633 enumerator lines; real messages = 1632". That
count includes 12 enumerators inside the `/* ... */` block at `MsgType.h:1309-1327`
that the C compiler never sees. The live count is **1621** (1620 messages plus the
terminator). No *value* is affected: the next real enumerator is an explicit rebase
back to 5000, and all 53 anchors plus all 157 annotations agree either way. Only
the headline count was off. The front and auth counts in §4.2 / §5.1 are correct.
